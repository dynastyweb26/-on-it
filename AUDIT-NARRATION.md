# AUDIT-NARRATION.md

## Overview

This audit investigates a discrepancy in the **On It** application (Next.js 14 App Router + Supabase) where an invoice card accurately rendered **$2,351.00** with a **40% deposit**, but the chat assistant's spoken/text reply stated **~$1,684.50**.

---

## 1. Where does the chat reply's total come from?

**Finding:** The chat reply's total comes directly from **the AI model writing its own number** as freeform text inside the JSON `reply` string field. Neither server-side nor client-side financial calculation utilities (`calculateInvoiceTotals`) compute or validate the dollar amount in the spoken/text `reply`.

### Code Trace (src/app/api/parse -> src/lib/ai.ts -> src/app/(app)/chat/page.tsx):

1. **AI Model Generation (`src/lib/ai.ts`):**
   - **File & Lines:** `src/lib/ai.ts`, lines 35–71, 74–118 (*verified by reading code*).
   - **Mechanism:** The Anthropic Claude Haiku model (`claude-haiku-4-5-20251001`) receives the `SYSTEM` prompt. The prompt instructs the model to produce a JSON object adhering to the `ExtractResult` interface, which includes a freeform `reply` field ("what On It says back — short, friendly, spoken-aloud-safe"). The LLM generates the text of `reply` (including any mentioned dollar figures) via text completion.

2. **Parsing Engine (`src/lib/ai.ts`):**
   - **File & Lines:** `src/lib/ai.ts`, lines 105–118 (*verified by reading code*).
   - **Mechanism:** `extract()` parses the raw JSON output using `parseJsonObject()`. The `reply` string generated by the model is passed through as part of `ExtractResult` without extracting or validating numerical figures mentioned within the prose.

3. **API Route Handler (`src/app/api/parse/route.ts`):**
   - **File & Lines:** `src/app/api/parse/route.ts`, lines 53, 68–76, 99 (*verified by reading code*).
   - **Mechanism:** The POST handler calls `extract(history, draft, today)`. Unless line items fail normalization (`hasInvalidLineItem`, line 72), `result.reply` is returned verbatim to the client in `NextResponse.json({ ...result, duplicateWarning })`. The server does not compute or substitute the monetary figures in `result.reply`.

4. **Client Chat Render & Speech (`src/app/(app)/chat/page.tsx`):**
   - **File & Lines:** `src/app/(app)/chat/page.tsx`, lines 538–543, 878–892 (*verified by reading code*).
   - **Mechanism:** In `send()`, the client receives `data.reply` (line 538) and appends it to state via `setMessages()` (line 539). The transcript maps over `messages` and renders `m.content` in JSX (lines 878–892). If the turn input source was voice (`source === 'voice'`), `speak(reply)` is invoked (lines 542–543), speaking the model's unvalidated text aloud.

5. **Client Confirmation Summary (`src/app/(app)/chat/page.tsx`):**
   - **File & Lines:** `src/app/(app)/chat/page.tsx`, lines 620–639 (*verified by reading code*).
   - **Mechanism:** When `finalize()` triggers `confirmSummary()`, a secondary client message is generated. Line 622 (`const total = items.reduce((s, li) => s + li.qty * li.unit_price, 0)`) performs a client-side sum of `qty * unit_price`, but ignores `tax_rate` and deposit structures, creating another divergence point for spoken text.

## 2. Where does the card's total come from?

**Finding:** The invoice card's total comes directly from `calculateInvoiceTotals` in `src/lib/financials.ts`.

### Code Trace:

1. **Card Preview Calculation (`src/app/(app)/chat/page.tsx`):**
   - **File & Lines:** `src/app/(app)/chat/page.tsx`, lines 833–841 (*verified by reading code*).
   - **Mechanism:** Before rendering the invoice card, `chat/page.tsx` computes `previewTotals` using `calculateInvoiceTotals`:
     ```typescript
     const previewItems = (draft?.line_items ?? []) as LineItem[];
     const previewDepositType = ((draft as any)?.deposit_type as DepositType) ?? 'none';
     const previewDepositValue = Number((draft as any)?.deposit_value ?? 0);
     const previewTotals = calculateInvoiceTotals(
       previewItems,
       draft?.tax_rate ?? 0,
       previewDepositType,
       previewDepositValue
     );
     ```

2. **Financial Math Engine (`src/lib/financials.ts`):**
   - **File & Lines:** `src/lib/financials.ts`, lines 75–149 (*verified by reading code*).
   - **Mechanism:** `calculateInvoiceTotals` computes:
     - `subtotal = calculateSubtotal(items)` (lines 80, 52–57)
     - `taxAmount = calculateTaxAmount(subtotal, taxRate)` (lines 81, 60–63)
     - `total = roundCurrency(subtotal + taxAmount)` (line 82)
     - `depositAmount` based on deposit type (`percentage` / `fixed`) and value (lines 88–95)
     - `remaining = roundCurrency(total - depositAmount)` (line 98)
     - `amountDueNow` (alias `dueNow`, lines 106–115, 141)

3. **Card Component JSX (`src/app/(app)/chat/page.tsx`):**
   - **File & Lines:** `src/app/(app)/chat/page.tsx`, lines 939–960 (*verified by reading code*).
   - **Mechanism:** The preview card renders:
     - "Project total": `money(previewTotals.total)` -> **$2,351.00** (line 943)
     - "40% deposit": `money(previewTotals.depositAmount)` -> **$940.40** (line 947)
     - "Remaining balance": `money(previewTotals.remaining)` -> **$1,410.60** (line 951)
     - "Deposit due now": `money(previewTotals.amountDueNow)` -> **$940.40** (lines 956–959)

## 3. How could $1,684.50 come about?

### Mathematical and Code Mechanics Analysis:

1. **Numerical Breakdown:**
   - **Invoice Total:** $2,351.00
   - **40% Deposit:** $940.40 ($2,351.00 x 0.40)
   - **60% Balance:** $1,410.60 ($2,351.00 x 0.60)
   - **Observed Chat Reply Figure:** ~$1,684.50
   - Note that $2,351.00 / 1.395665 ≈ $1,684.50 (or $1,684.50 x 1.40 ≈ $2,358.30).

2. **Contributing Factors & Scenarios:**
   - **Scenario A: Chat-requested deposits becoming line items (`src/lib/ai.ts` lines 21, 55, *verified by reading code*):**
     In `src/lib/ai.ts`, the `ExtractResult` interface lacks explicit schema fields for `deposit_type` and `deposit_value`. System instructions at line 55 direct the AI to capture deposit terms in `notes`. However, when a user dictates a deposit in chat (e.g., "add a 40% deposit"), the model often inserts a negative line item or subtracts line items incorrectly (e.g., subtracting $666.50 from $2,351.00, yielding $1,684.50). If line items in `draft.line_items` are modified to total $1,684.50, the AI states $1,684.50 in its reply string.
   - **Scenario B: Stale Draft State & Multi-Turn Context (`src/app/api/parse/route.ts` lines 35, 47, *verified by reading code*):**
     `/api/parse` receives `draft` from the client. In a previous turn, line items may have totaled $1,684.50. When the user added additional items bringing the card total to $2,351.00, the LLM generated its `reply` text referencing the subtotal from `currentDraft` ($1,684.50) before completing the full line item array addition ($2,351.00).
   - **Scenario C: Tax Rate & LLM Mental Arithmetic Error (`src/lib/ai.ts` lines 35–71, *suspected*):**
     LLMs frequently make arithmetic errors when estimating totals in freeform prose. For instance, if a 40% rate was mentioned, the model may have attempted to divide $2,351.00 / 1.40 (= $1,679.28) and hallucinated $1,684.50, or computed subtotal before a 40% tax addition.
   - **Scenario D: `confirmSummary()` line item sum (`src/app/(app)/chat/page.tsx` line 622, *verified by reading code*):**
     `confirmSummary()` calculates `total = items.reduce((s, li) => s + li.qty * li.unit_price, 0)`. If line items were manipulated into $1,684.50 without tax/deposit inclusion, `confirmSummary()` speaks $1,684.50 while the card displays $2,351.00.

3. **Is "chat-requested deposits become line items" the same root cause?**
   **YES (*verified by reading code*).** Both bugs stem from the same architectural deficiency:
   - `ExtractResult` lacks explicit deposit schema fields (`deposit_type`, `deposit_value`), forcing the model to handle deposit requests via line items, notes, or mental math in `reply`.
   - Spoken/text responses in chat are generated as freeform LLM prose instead of being derived deterministically from `calculateInvoiceTotals`.

## 5. Recommended Fix (Ordered List of Commits)

To ensure that spoken/text totals always originate from the exact same calculation as the card (`calculateInvoiceTotals`), the following ordered series of commits is recommended (*do not implement*):

### Commit 1: Add deposit schema fields to `ExtractResult` and system prompt in `src/lib/ai.ts`
- Update `ExtractResult` interface in `src/lib/ai.ts` to include `deposit_type: DepositType | null` and `deposit_value: number | null`.
- Update the system prompt in `src/lib/ai.ts` instructing the model to extract explicit deposit requests (e.g. "40% deposit", "$500 deposit") into `deposit_type` and `deposit_value` rather than modifying `line_items` or embedding deposits into `notes`.
- Update `src/app/api/parse/route.ts` to validate and normalize `deposit_type` and `deposit_value`.

### Commit 2: Enforce server-side reply text interpolation using `calculateInvoiceTotals` in `src/app/api/parse/route.ts`
- In `src/app/api/parse/route.ts`, after line items and tax/deposit fields are normalized, invoke `calculateInvoiceTotals(result.line_items, result.tax_rate ?? 0, result.deposit_type ?? 'none', result.deposit_value ?? 0)`.
- Replace any dollar amounts in the model's generated `result.reply` with `money(totals.amountDueNow)` or `money(totals.total)` computed by `calculateInvoiceTotals()`, guaranteeing that the spoken/text turn reply matches the card calculation exactly.

### Commit 3: Refactor `confirmSummary()` in `src/app/(app)/chat/page.tsx` to use `calculateInvoiceTotals`
- Refactor `confirmSummary()` in `src/app/(app)/chat/page.tsx` to call `calculateInvoiceTotals(items, draft?.tax_rate ?? 0, depositType, depositValue)` instead of doing manual `items.reduce((s, li) => s + li.qty * li.unit_price, 0)`.
- Ensure the confirmation summary explicitly states project total, deposit due now, and remaining balance using derived `FinancialTotals` properties (`total`, `depositAmount`, `remaining`, `amountDueNow`).

### Commit 4: Add unit tests for chat financial synchronization in `src/lib/financials.test.ts`
- Add unit tests verifying that `calculateInvoiceTotals()` produces consistent calculations across line items, tax rates, percentage deposits, fixed deposits, and zero deposits.
- Assert that formatting outputs (`money()`) match between chat reply generators and card rendering pipelines.
